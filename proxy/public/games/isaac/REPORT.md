## 1. 技术选型与理由

| 项 | 选择 | 理由 |
|---|---|---|
| 渲染 | 原生 **Canvas 2D** + 手写 `requestAnimationFrame` 循环 | 需求核心是"素材全部用代码绘制"，工作量集中在程序化绘图函数上；Phaser/PixiJS 提供的精灵图管线、物理、场景树在这里几乎用不到，只会增加体积并妨碍 `file://` 直开 |
| 语言/构建 | 原生 ES2020，**无构建、无 npm 依赖**，普通 `<script>` 标签 | 交付要求"最终必须能在浏览器直接打开游玩"；ES module 在 `file://` 下会被 CORS 拦，所以刻意不用 module |
| 逻辑分辨率 | 固定 900×540（15×9 格 @ 60px），CSS transform 缩放 | 对齐原作 13×7 可行走格的房间比例；坐标全部可写死，省掉分辨率无关逻辑 |
| 随机 | mulberry32 播种 PRNG | 同 seed 可复现整层地牢，bug 可重放，测试可断言 |
| 音效 | WebAudio 实时合成（方波/锯齿/白噪 + 包络） | 同样不引入外部资源 |
| 测试 | Python Playwright（本机）+ 页面内 `window.__game` | 真键盘真触控驱动 + 结构化状态断言 |

游戏本体 5039 行，其中 `js/art.js`（程序化绘图）1299 行，是最大的单个模块——
这符合预期：需求把"素材用代码绘制"作为硬要求，绘图就是主要工作量所在。

## 2. Firecrawl 联网搜到的原作机制要点

### 2.1 地牢生成算法（决定性资料）
**来源**：<https://www.boristhebrave.com/2020/09/12/dungeon-generation-in-binding-of-isaac/>
（Boris the Brave 对原版源码的逆向分析）

这篇是本次最有价值的一手资料，直接给出了原作楼层生成的完整算法，我按它 1:1 实现：

- 地牢建在 **9×8 网格**上，起始房固定在中间（原文用 `35` 编号，即 x=5,y=3）
- 房间数公式 `random(2) + 5 + level * 2.6`，即首层 7–8 间、每层递增 2–3 间
- 从起始房入队做 BFS，对每个格子的四个方向依次判断，命中任一条则放弃该方向：
  1. 邻格已被占用
  2. **邻格自身已有超过 1 个已填充邻居**
  3. 房间数已够
  4. **50% 概率直接放弃**
- 第 2 条是关键：它保证地牢是"分叉的走廊"而**永远不会形成环路**
- 没有向任何邻居扩张的格子记为**死胡同（end room）**
- **Boss 房取死胡同列表的最后一项**——由于是向外广度扩张，它必然是离起点最远的房间之一
- 其余特殊房（商店、宝物房、祭祀房…）也基本都放在死胡同上
- 生成后做一致性校验：房间数必须正确，且 **Boss 房不能与起始房相邻**，否则整层重新生成
- 相邻房间的门**永远开在共享墙正中**，且每间房都被设计成从四个方向都能走通——
  所以选房间内部布局时不需要额外考虑连通性
- 房间内容从难度分池（easy/medium/hard）里抽取；`Basement` 池有 174 个普通房布局

**我的实现差异**：需求规定"每层 5–8 个房间"，所以房间数改成 `clamp(4 + level + rand(0,1), 5, 8)`
（第 1 层 5–6、第 3 层 7–8），并把宝物房也计入总数；其余规则（>1 邻居拒绝、50% 放弃、
死胡同放 Boss、Boss 不邻起点、失败重生成）完全照搬。200 次随机种子校验全部合法。

### 2.2 敌人行为
**来源**：<https://bindingofisaacrebirth.fandom.com/wiki/Monsters>

- **Gaper**：朝以撒走，接触伤害；"闭着眼睛，获得视线后眼睛睁开并**永久加速**"
  → 我实现了 `awake` 状态，进入 300px 视野后速度 ×1.35 且不可逆
- **Gurgle / Crackle** 等变体是"边走边吐"，说明原作大量敌人是"移动模式 × 攻击模式"的组合
  → 我据此把 5 种敌人设计成移动与攻击两个维度都不重复（追击/悬停游走/完全固定/
  高速乱窜/跳跃逼近 × 接触/单发瞄准/三连扇形/无/四向十字）

### 2.3 Boss：Monstro
**来源**：<https://bindingofisaacrebirth.fandom.com/wiki/Monstro>、
<https://bindingofisaacrebirth.wiki.gg/wiki/Monstro>、
<https://www.reddit.com/r/bindingofisaac/comments/68hyoe/boss_workshop_27_monstro/>

要点：
- "**朝以撒方向跳跃**"
- "咳出一大团**杂乱无章的眼泪**"
- "**跳出画面，瞄准玩家头顶落下**"
- "**大颗眼泪造成 1 颗心伤害，小颗造成半颗心**"

→ 我的 Monstro 状态机完全按这三段设计：`hopCharge→hop`（蓄力压扁→跳跃→落地冲击波）、
`vomitCharge→vomit`（张嘴→散射，随机大小弹，大弹 2 半心/小弹 1 半心）、
`slamCharge→slamUp→slamDown`（蓄力→跳出画面高度 420px→追踪玩家落点，
地面画红色虚线预警圈→砸地 + 环形弹幕）。血量 50% 以下进入 `rage`，间隔缩短、弹量增加。

## 3. Context7 查询记录

1. `resolve-library-id("MDN Web Docs")` → `/mdn/content`
2. `query-docs(/mdn/content, "Canvas 2D context game loop with requestAnimationFrame,
   imageSmoothingEnabled for pixel art, radial gradient, shadowBlur, offscreen canvas
   caching for sprites")`

拿到并实际用上的内容：
- `requestAnimationFrame` 游戏循环的标准写法（清屏 → 更新 → 绘制 → 递归请求），
  确认了"不要用 setInterval 驱动渲染"
- `createRadialGradient` 的双圆构造与 `addColorStop` 用法 → 用在角色高光 `sheen()`、
  基座圣光、坑洞内部、暗角后处理、Boss 环境光遮蔽
- `OffscreenCanvas` / 离屏 canvas 缓存 → 决定把每间房的地板**烘焙一次**到离屏 canvas
  再逐帧 `drawImage`，而不是每帧重画上千个噪点（这是帧率能稳在 94–114fps 的主要原因）
- Crisp pixel art 一节说明 `image-rendering: pixelated` + 整数倍缩放的配套关系；
  因为本作是矢量卡通风而非像素画，最终**选择不启用** pixelated，保持 `imageSmoothingEnabled = true`

## 4. Loop Engineering 迭代记录

### 轮 1 — 一个房间 + 移动射击 + 敌人（打通全链路）
按需求的推进顺序，但我把"先做一个房间"扩展成一次性搭出完整骨架
（util / art / dungeon / items / entities / game / main + 调试接口），
然后立刻写 Playwright 测试脚本从头到尾驱动一遍。

**结果**：第一次运行 **52/52 断言全部通过**，无 console 报错，106fps。
移动、射击、敌人掉血、清房开门、房间切换、道具生效、Boss 状态机、死亡/通关界面全部一次跑通。

**但截图复查发现一堆美术问题**（这正是"截图自检"的价值——断言全绿不等于好看）：

| 问题 | 修法 |
|---|---|
| Monstro 太小（r=52），和普通敌人差不多大，且颜色与地板撞色 | 半径 52→64→76，改用更饱和的病态肉色，描边加粗到 7，加环境光遮蔽 |
| 开着的门是一块纯黑矩形，像画面破洞 | 改成"向内递进的走廊渐变 + 拱券 + 门框砖缝 + 门板缩进 + 暖光溢到地面 + 门槛石" |
| 石头是扁平的五边形 | 给 `blob()` 加中点二次曲线平滑 + 振幅参数，改成扁圆卵石 + 顶光渐变 + 凿痕 |
| 地板棋盘感太强 | 砖缝对比度调低、加 26 处大尺度有机斑块打散网格 |
| 朝上时后脑是一颗没有细节的白蛋 | 加头顶渐变 + 后颈折线 + 两根发丝 |
| 道具提示 toast 堆在屏幕正中挡住战斗 | 移到顶部、缩小、最多显示 3 条 |
| 楼层横幅是一条生硬的黑色信箱条 | 改成上下淡出的渐变带 + 文字投影 |
| 标题界面中间空着 | 画了砖墙背景 + 干涸血渍 + 身后透光的门洞 + 2.85 倍大的以撒 + 脚下血泊/泪泊 |

### 轮 2 — 命中反馈与地形可读性
**截图发现**：玩家受击时被一个巨大的粉红色圆糊住整个身体（`hitFlash` 用了
`globalCompositeOperation='lighter'` 画 26×30 的实心椭圆）；坑洞是纯黑的洞，缺少石缘。

**修法**：
- 受击反馈从"盖一个色块"改成"**贴合轮廓的红色描边 + 外发光 + 极低透明度叠加**"，
  头部和躯干各描一圈；敌人受击同理改成白色描边 + 12px 发光 + 0.42 透明度叠加
- 坑洞加"破碎石缘（顶光渐变）+ 洞内暖黑径向渐变（不用纯黑）+ 上缘接光的高光弧"
- 五种敌人尺寸整体上调（17→20 等），并发现**硬编码的五官偏移量是按旧半径调的**，
  改半径后脸和身体会脱节 → 引入 `enemyScale(ctx, e, refR)`：
  **在固定参考半径下作画，再整体缩放**，之后调碰撞半径不会再破坏比例

### 轮 3 — 机器人试玩暴露真实可玩性问题（本轮价值最大）
截图只能证明"好看"，证不了"能玩"。所以我写了 `test/bot.js`：一个**只通过和人类相同的
输入接口**（`__game.press/release/move`）操作的页面内机器人，然后跑多局无作弊试玩。

**第一次机器人试玩：6 局全部在第 2 个房间内 20–34 秒暴死，平均只有 2.7 击杀。**
断言全绿的游戏，实际根本不能玩。逐项定位：

1. **击退是假的**。`takeDamage` 里 `vx += n.x*250`，但移动代码每帧
   `approach(vx, targetVx, 2600*dt)`，两帧内就把冲量抹平 → 无敌帧一结束怪还贴着你，
   立刻挨第二下，形成死亡螺旋。
   **修**：加 0.2s **硬直**（`hitStun`），硬直期间输入不接管速度，只做阻尼；击退提到 430。
2. 敌人血量偏高、接触伤害偏重 → Gaper 9→7、Horf 13→10、Clotty 16→12、Pooter 8→6、Fly 4→3，
   逐层血量成长 0.22→0.15。
3. **开门瞬间白送伤害** → 敌人加 0.55s（Boss 0.9s）**具现化保护期**，期间不动不攻击不判接触，
   并配浮现动画（从地面升起 + 淡入 + 收缩光环）让玩家看得懂。
4. 掉落率上调（击杀 16%→20%、清房 45%→60%）。
5. 顺手加了**命中停顿**（hit-stop，命中冻结 2–4 帧）——很便宜，但"打到了"的手感几乎全靠它。

**第二次机器人试玩：不再暴死，但 6 局全部卡在同一个房间不动，140 秒只有 2–4 击杀。**
打日志逐帧 dump 状态，抓到两个真 bug：

6. **清房奖励会掉进坑里，永远拿不到**。房间清空后奖励固定生成在房间正中
   `(450,270)`，而 `pitField` 布局的坑正好占着正中那格。机器人于是永远朝一个拿不到的
   心走过去。
   **修**：加 `findFreeSpot(x, y, clearance)`——先判原位，不行就螺旋向外搜，
   最后兜底扫全格；`dropPickup` 与 Boss 奖励基座/活板门都走它。
7. **坑洞阵可以把玩家夹死**。坑碰撞半径 `r*0.84 + 15`，相邻坑中心距 60，
   斜向缝隙只剩 9.5px，玩家挤进斜缝后两个法向互相抵消，动不了。
   **修**：坑半径 27→25、玩家对障碍的碰撞系数 0.84→0.76，把斜向缝隙放宽到可通行。
8. 机器人本身也不合格：四向射击**必须先在某一轴对齐才打得中**，而它一直斜着开枪。
   **修**：`aim()` 改为选"更接近对齐的那根轴"，且只在错位小于 `r+26` 时才扣扳机；
   走位改成"补齐垂直轴 + 在射击轴上维持 200px"；加绕障切向力和卡住脱困。

**第三次机器人试玩：0 死锁，但仍 0 Boss 击杀。**
把伤害来源打上标签（`contact:xxx` / `tear` / `spikes` / `monstro:hop` / `monstro:slam`）后，
结论非常干净：

> **每局都清掉了 4/5 个普通房，全程只掉 3–4 点血，然后死在 Boss 手里。**
> 伤害来源 90% 是 `contact:monstro`。

也就是说普通房难度已经调好了，**问题 100% 在 Boss 战**。同时发现一个测试方法学问题：

9. **测试预算按挂钟计不成立**。本机同时跑 7 个 Agent，页面拿不到 60fps
   （最差 905 秒挂钟只推进 8.3 游戏秒）。8 局跑了 90 分钟，多数局是被挂钟截断而非打输。
   **修**：预算改成按**游戏内时间**（`snapshot().elapsed`）计，外层只留一个宽松的挂钟保险丝；
   另外写了 `test/bossfight.py` 直接把机器人塞进 Boss 房实战，**80 秒**就能判定
   Boss 战是否可胜，取代此前 90 分钟的全流程等待。

10. Boss 战本身的公平性修正：
    - **Boss 身体只在真正扑击时造成伤害**（`hop`/`slamDown`/`dash`），
      站在待机的 Monstro 旁边不再持续掉血——这也更接近原作（威胁来自跳跃和砸地，不是贴着他）
    - Boss 接触判定半径收紧（`r*0.8 + p.r*0.55`）
    - Monstro 呕吐弹量几乎砍半（间隔 0.07→0.1s、每次 2–3→1–2 颗），原作大约 10 颗量级
    - 落地冲击波/砸地伤害半径从 `r+42` / `r+54` 收到 `r*0.75+32` / `r*0.8+38`，让预警圈和真实危险区对得上
    - 环形弹幕 8/12→6/9 颗，狂暴期落地附加弹 4→2
    - Boss 血量 Monstro 210→160、Duke 185→140；跳跃速度 370→330、跳跃间隔与恢复拉长
    - 起始生命 3 心→**4 心**（原作 Magdalene 就是 4 心，仍在原作设定内），
      多出来的血几乎全部花在 Boss 战上，正是最需要的地方
    - 机器人也补上 Boss 专属走位：站得更远（330px）、Boss 蓄力/冲刺/高跳时侧向拉开、
      先探索完普通房再打 Boss（人类本来就这么玩）

**修正后 `test/bossfight.py`：4/5 击杀，平均打掉 99% Boss 血量**，且两次失手都有意义
（零道具那局仍把 Boss 打到 17%，说明构筑真的有用）。
`test/botrun.py`（300 游戏秒预算）：3 局累计击败 **3 个 Boss**、2/3 局推进到第 2 层以上、
**其中 1 局已打到最终第 3 层**（42 击杀 / 5 道具，被预算而非死亡截断）、0 死锁、0 报错。

### 轮 4 — 移动端真机视口复查
用 414×896 手机视口截图，发现**画布被压缩且裁切**，只显示房间的一小块。

11. `#stage` 是 flex 子项，固定 900px 宽在 414px 视口里**先被 flex-shrink 压扁**，
    再叠加 transform 缩放，`overflow:hidden` 把超出部分切掉。桌面端因为视口比 900 宽，
    从没触发过，所以前面所有测试都没抓到。

    **并补了 2 条回归断言**（画布尺寸必须等于等比缩放值、必须完整落在视口内），

## 7. 结论与不足

**做到了**：需求列出的全部系统——原作算法级的随机地牢（5–8 房 + 门连接 + Boss 房 + 宝箱房 + 小地图）、
射击战斗（射速冷却 / 击退 / 命中停顿 / 受击闪光 / 粒子 / 永久血渍）、
5 种移动与攻击模式各异的普通敌人 + 2 个多段状态机 Boss、20 件可叠加且改外观的道具、
6 维属性 + 常驻属性面板、开始/死亡/通关三界面与完整三层流程、
桌面键盘 + 移动端摇杆与射击按钮双操控、全程纯代码绘制的暗黑卡通美术。

**不足**：
- Boss 只有 2 种，第 3 层复用强化版 Monstro；原作那种"每层不同 Boss 池"没做
- 没有商店/祭坛/诅咒房/炸弹/钥匙/饰品/主动道具，道具限于 20 件被动
- 房间只有标准 1×1 形状（原作 Rebirth 才加入 2×2、L 形异形房）
- 敌人没有原作的"死亡后变异"（Gaper→Pacer/Gusher）与冠军怪变体
- 竖屏手机画面偏小（受 5:3 房间比例所限），需要横屏才够舒展
- 平衡是靠机器人试玩调的，机器人走位远不如人类，所以它的通关率只是**可玩性下限**；
  真人手感仍需人工试玩微调

## B. 关键设计决策

### B.1 Boss 池而不是"每层一个 Boss"
12 层配 13 个 Boss，如果一一对应，那第二次玩的路线完全一样。
改成每个章节带一个 2 选 1 的池子（第 9–12 层各只有一个，因为原作里 Hush/Satan/Isaac/???
本来就是唯一层主），并让 `generateFloor` 收一个 `usedBosses` 列表**优先挑本局没出现过的**。
效果：前 8 层每局的 Boss 序列都不一样。

### B.2 命中判定抽象为 `enemyHitPoint()`
新增的蠕虫型 Boss（Larry Jr. / Chub / Scolex）身体是一串跟随的节，而 Scolex **只有尾巴能打**。
原来的 `dist2(t.x, t.y, e.x, e.y) < (e.r + t.r)²` 表达不了这些。
抽出一个函数，由 `def.hitSegs`（`true` / `'tail'` / 不设）决定，
所有子弹、激光、接触伤害都走它。加 Boss 时不用再改碰撞代码。

### B.3 Boss 接触伤害从"状态名白名单"改成 `e.aggro`
原来 game.js 里硬编码 `['hop','slamDown','dash'].includes(e.state)`，
加到 13 个 Boss 就会变成一长串状态名。改成每个 Boss 的 AI 自己每帧设 `e.aggro`，
game.js 只读这个布尔值（老的两个 Boss 保留白名单兜底，避免无谓改动）。

### B.4 血肉章节换一套地板烘焙
Womb / Utero / ??? 如果只是把石砖调成红色，看起来就是"红色的地下室"。
给 `THEMES` 加了 `flesh` 标记：命中时 `bakeFloor` **完全跳过瓦片循环**，
改画层叠的肉瓣 + 爬行血管 + 毛孔，`drawWalls` 也跳过砖缝改画搏动的膜。
同理 `bones` / `ember` / `holy` 三个标记分别烘出骨骸、余烬、大理石纹与彩窗光。

## C. 开发中真正踩到并修掉的问题

### C.1 【最重要】难度曲线：线性血量在后期彻底失效
第一版沿用原来的 `1 + (层数-1)*0.04` 线性缩放，跑完 13 场 Boss 战发现：

```
L10 satan     707 HP  ->  5.5s 秒杀
L12 blueBaby  893 HP  ->  5.9s 秒杀
```

原因是**玩家输出是复利的**——每件道具都在上一件的结果上加或乘，
而血量是线性的，两条曲线在第 5 层左右就交叉了。

改成指数后又矫枉过正（用 1.38 时第 12 层 90 秒只打掉 21%）。
于是干脆**别猜了**：写了 `test/calibrate.py`，让机器人在每层的 Boss 房打一个
无限血、不还手的靶子，实测 18 游戏秒的输出：

```
L1  DPS=9.2     L5  DPS=52.0    L9   DPS=165.0
L2  DPS=18.4    L6  DPS=122.0   L10  DPS=216.9
L3  DPS=15.3    L7  DPS=96.3    L11  DPS=77.3
L4  DPS=20.4    L8  DPS=64.9    L12  DPS=181.4
```

噪声不小（机器人在不同 Boss 房的走位差异很大），但趋势清楚：**总增长约 20 倍，不是 50 倍**。
`20^(1/11) ≈ 1.31`，最终取 Boss `1.28^(层数-1)`、杂兵 `1.24^(层数-1)`，
并把后期 Boss 的基础血量一并下调（satan 520→360、blueBaby 620→360）。
重测后 13 场的用时落在 **9.5s – 74.6s**，绝大多数在 12–39s。

教训：**难度数值不该用算术推，应该用测量定。** 我一开始按"伤害×射速×弹数"
算出玩家有 490 DPS，实测只有 50–180——因为四向射击必须走位，实际开火占空比很低。

### C.2 【最重要】测试机器人自己有 bug，掩盖了真实覆盖率
第一次跑 12 层全流程试玩，3 局里有 **2 局卡在第 1 层空转 420 游戏秒**，只杀了 4–7 只怪。
一开始以为是新加的房间布局堵死了通路，逐帧打日志才看清真相：

```
px=145 py=389   horf(572,391) hp=7   ← 位置几乎不动，敌人血也不动
botlog: ['unstuck','unstuck','unstuck', ... ×18]
```

机器人**站在一块石头后面，朝着石头射了 400 秒**。三个叠加的缺陷：

1. 它不检查射线上有没有挡住眼泪的障碍物；
2. 战斗时的避障只有斥力没有切向分量 → 卡在"石头斥力"和"目标引力"的局部最小值里；
3. 它有"别贴墙"的约束 `if (p.y > 390) my -= 1.5`，而那只 Horf 在 y=450 的角落——
   **它永远不可能在 y 轴上对齐这只敌人**。

三条都修了：加 `lineBlocked()` 射线检测（挡住就侧移让开而不是继续射）、
避障加切向分量、**对齐用的那条轴不再受贴墙约束**。
另外补了"目标超出射程时主动贴近"（原来会停在射程边缘干射）。

改完同样 4 局：累计击败 Boss **4 → 9 个**，最远推进 **第 1 层 → 第 6 层**（14 件道具）。

教训：**当自动化测试给出"打不过"的结论时，先怀疑测试自己。**
这三个 bug 全是老代码里就有的，只是 3 层的时候没有暴露得这么难看。

### C.3 坑洞可以把房间正中变成死路
新加的 `pitField` / `twinPits` 布局会在房间正中放坑。门前通道虽然被保护了，
但**正中那一格没有**——上下门的通道各自延伸到 (6,2) 和 (6,4)，中间的 (6,3) 是坑，
于是上下贯穿被切断，玩家得绕一大圈。加一行把 `'6,3'` 永久放进保护集合。

### C.4 美术复查抓出的 6 个问题
每层 + 每个 Boss 各截一张图逐张看，改掉：

1. **??? 只有一颗头**——身体画在 `R*0.62`、脑袋半径 `R*0.82`，整个身子被脑袋盖住了。
   身体下移到 `R*0.92` 并把头缩到 `R*0.78`。
2. **撒旦像个没有脸的土豆**——角太小、手臂贴在身上像胸部。
   换成大盘角（带年轮刻痕）+ 张开的手臂和爪子 + 山羊吻部 + 发光眼缝。
3. **妈妈的脚看不出是脚**——原来是个白圆饼加一条黑带。
   改成前宽后窄的脚掌轮廓 + 足弓阴影 + 五个由大到小的脚趾。
   另外脚抬到 340px 高时会缩进顶墙看不见，改成按房间高度**限制绘制高度**（判定不变）。
4. **Womb 的墙上还有砖缝**——`drawWalls` 的砖块循环没有跳过 flesh 主题。
5. **Catacombs 的骨头像哑铃**——尺寸砍半、透明度从 0.18–0.4 降到 0.1–0.22。
6. **深层小地图盖住战场**——13 间房的地图铺开后压到右上角的敌人。
   按网格跨度自动把格子缩到 72%。

### C.5 敌方激光会和玩家的 Brimstone 撞色

## F. 追加轮的不足

- **机器人没有完整通关过 12 层**。它每层大约要花 100 游戏秒，12 层就是 1200 秒预算，
  在这台并行跑多个 Agent 的机器上是几小时挂钟。目前最好成绩是第 6 层 / 5 个 Boss。
  所以"12 层可通关"是**分段验证**的（每个 Boss 单独可胜 + 全流程无死锁），
  不是一次性端到端验证的。
- **难度是照机器人标定的**，人类比机器人强得多，对人来说前中期可能偏轻松。
- 55 件道具**全部是被动**的，没有主动道具/充能系统。
- Boss 的第二形态只有"数值变化 + 增加弹幕种类"，没有原作那种真正的形态切换
  （比如 Hush 第一阶段是另一个模型）。
